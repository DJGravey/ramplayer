# Video playback: H.264 and H.265 in MP4 — rapid plan (phase one)

**Mode:** rapid   **Date:** 2026-09-17
**Goal:** `ramplayer shot.mp4` plays an H.264 or H.265 file the way an EXR
sequence plays today: frames decoded on loader threads into the RAM cache as
display-ready 8-bit images, scrubbed, stepped and played in either direction
through the same transport, with the same timeline and residency band. FFmpeg
does the demuxing, decoding and colour conversion, dynamically linked and
LGPL. Constant frame rate only. No audio. The cache learns that video frames
come in groups: one thread decodes a whole group from its keyframe, handing
each frame over as it lands, and a thread that stops part way keeps its place
so forward playback is one linear decode. The cache also keeps a reserve of
about one group behind the playhead, whichever way it is moving, so a
reversal plays from RAM while the loaders turn around. Left for a later
phase: variable frame rate, HDR tone mapping, rotation metadata, hardware
decoding, and reverse play across groups larger than the budget.

## Steps Summary
1. `vcpkg.json`/`CMakeLists.txt`: FFmpeg (avcodec, avformat, swscale, avutil), vcpkg on Windows, pkg-config elsewhere.
2. `sequence.c`/`sequence.h`: a video kind: one path, a frame count and rate, and per-frame group boundaries from the container index.
3. `reader.h`/`reader.c`/`reader_exr.c`: a per-thread `Reader` that loads a range of frames and delivers each one; the EXR backend behind it, unchanged in what it decodes.
4. `reader_video.c` (new): the FFmpeg backend: index, seek to a group, decode forward, convert to BGRA, continue without seeking when the next request follows on.
5. `cache.c`/`cache.h`: group claims, incremental delivery, early stop at the loaders' reach, and the reserve behind the playhead in the value function.
6. `main.c`: video inputs skip the EXR probe, video worker and decoder thread defaults, `--readers` not applied to video, usage text.
7. `tools/make_test_video.sh`: fixtures; `tests/test_reader.c` and `tests/test_player.c`: index, decoding, groups, scrubbing, reserve; README.

## Approach

### The FFmpeg dependency
FFmpeg 8.1.1 from the pinned vcpkg registry, with `default-features` off and
only `avcodec`, `avformat` and `swscale` on (avutil comes with them). H.264
and H.265 decoding are native to libavcodec, so no x264 or x265 and the build
stays LGPL. The x64-windows triplet builds DLLs, which is what LGPL asks of an
MIT program; vcpkg's post-build step already copies SDL2.dll beside the exe
and will do the same for the FFmpeg DLLs. The first configure builds FFmpeg
from source through its own configure script (vcpkg fetches MSYS2 for it)
and takes tens of minutes; later configures hit the binary cache. On Linux
the four libraries come from pkg-config as `libavcodec libavformat libavutil
libswscale`, the same fallback shape SDL2 and OpenEXR use. The code targets
the FFmpeg 5+ API only: `avcodec_send_packet`/`avcodec_receive_frame`,
`AVCodecParameters`, `avformat_index_get_entry()`, `sws_scale_frame()`.

### Video as a Sequence
`Sequence` gains `kind` (`SEQ_IMAGES`, `SEQ_VIDEO`), `fps` (the container's
average frame rate, 0 for images), and for video two per-frame arrays,
`group_start[]` and `group_end[]`, giving the first frame of the group a
frame belongs to and one past its last. `frames[i].number` is `i`. `path` on
each frame is NULL for video; the file is `seq->video_path`. A single input
whose extension is `.mp4`, `.m4v` or `.mov` opens as video; a directory or a
list of inputs never does. `sequence_open()` fills the video fields from
`reader_video_index()`, which opens the container, picks the first video
stream, and reads its packet index: the entry count is the frame count and
entries flagged as keyframes are the group starts. MP4 carries that index in
its header, so this reads no frame data. Frame `i` sits at
`start_pts + i * duration` in the stream's time base, derived from the
average frame rate: the constant-rate assumption, applied everywhere.
`nb_frames` and the duration are fallbacks for a container without an index.

Keyframe entries are in decode order and frames are numbered in display
order. For closed groups, which every common encoder produces by default,
these agree. For open groups a few leading frames belong to the previous
group in display order; the table is then a scheduling hint that is a frame
or two off, and correctness does not depend on it, because the decoder maps
every frame it produces by its own timestamp (below) and the cache drops
anything it did not ask for.

### The Reader interface
Today `reader_load()` takes a path and returns one image. Video needs a
stateful decoder per thread and produces runs of frames, so `reader.h` gains:

    typedef struct Reader Reader;
    Reader *reader_open(const Sequence *seq, const ColorLUT *lut, char *err, size_t errsz);
    void    reader_close(Reader *r);

    /* Called for each frame of a range as it is decoded, in order. `im` is
     * NULL when that frame failed to decode; the range continues. Returns 1
     * to go on to the next frame, 0 to stop. Takes ownership of `im`. */
    typedef int (*ReaderDeliver)(void *ud, int frame, Image *im);

    /* Decodes frames from..to-1 in order, delivering each. Returns 1 when the
     * range ended or the callback stopped it, 0 with `err` set when the
     * reader itself failed (a bad seek, a read error) or was cancelled
     * (`READER_ERR_CANCELLED`); frames not yet delivered are then untouched. */
    int reader_load_range(Reader *r, int from, int to, ReaderDeliver deliver, void *ud,
                          const atomic_int *abort_flag, char *err, size_t errsz);

A `Reader` is a small struct with an ops pointer; `reader.c` (new, tiny)
dispatches `reader_open()` on `seq->kind` to the EXR or video backend. The
EXR backend wraps the existing decoder: `from` is the frame, `to` is
`from + 1`, and the current path-based `reader_load()`, `reader_probe()`,
`DecodeScratch` and `reader_set_readers()` stay exactly as they are, since
`test_reader` drives them directly and nothing about EXR decoding changes.

### The video backend
Demuxing sits behind a small internal interface inside `reader_video.c`, so
an own MP4 demuxer can replace libavformat later without touching the
decoder, the cache or the tests: `demux_index()` builds the frame count,
rate, dimensions, codec parameters and group table from a file;
`demux_open()`/`demux_close()` give a per-thread handle; `demux_seek(group)`
positions it at a group's keyframe; `demux_read(packet)` returns the next
packet in decode order. The libavformat implementation of that interface is
about a hundred lines. Each `Reader` owns one demux handle, an
`AVCodecContext` with libavcodec frame threads, a `SwsContext` and one
`AVFrame`. A frame's index is
`llround((pts - start_pts) / duration)`; that mapping, not the packet count,
is the source of truth for which frame a decoded picture is.

`reader_load_range(from, to)` first decides whether to seek. The reader
remembers `next`, the index of the frame the decoder will produce next. If
`next == from`, or `next < from` with no group start in `(next, from]`, it
just keeps decoding, discarding pictures until `from`. Otherwise it seeks:
`avformat_seek_file()` to the timestamp of `group_start[from]` with
`AVSEEK_FLAG_BACKWARD`, flushes the decoder, and decodes forward discarding
pictures whose index is below `from`. If the first picture out is already
past `from`, which the decode-order index can cause on open groups, it seeks
again one group earlier. That is the whole of frame-accurate seeking.

Each decoded picture within the range is converted with `sws_scale_frame()`
into a fresh `Image`, `AV_PIX_FMT_BGRA` being exactly the `0xAARRGGBB`
little-endian layout `draw.c` wants, and delivered. The conversion sets the
matrix and range from the stream (BT.709 or BT.601, limited or full), takes
8-bit and 10-bit 4:2:0 alike, and relies on libavcodec's default cropping so
1080 lines coded as 1088 come out as 1080. Video is display-referred, so the
linear-to-sRGB table is not applied. At the end of the stream the decoder is
drained with a NULL packet so the last group's trailing pictures come out.

The abort flag is polled once per packet. Video honours a soft cancel at the
next frame boundary, since every frame already delivered is kept and nothing
in flight is worth finishing for its own sake; the EXR half-way rule stays
where it is, in the EXR decoder. A frame whose packet fails to decode is
delivered as NULL and the range goes on; a seek or read failure ends the
range with 0.

Threads: `reader_set_decoder_threads(n)` (a global like
`reader_set_readers()`) sets libavcodec's `thread_count` per decoder.
`main.c` gives video 2 loader threads by default and
`max(1, (cores - 1) / 2)` decoder threads each; `--threads N` sets the
loader count for both kinds. Two decoders each holding H.265 reference
pictures is tens to a few hundred megabytes outside the cache budget,
documented in the README as `--readers` buffers are.

### Group claims in the cache
`pick_locked()` is unchanged: the most valuable empty frame within reach that
the admission test lets in. What the worker does with the pick changes. It
asks the sequence for the pick's group `[gs, ge)` (for images `[f, f + 1)`),
walks back from the pick over empty frames to find `from` (so a backwards
pick takes the earlier frames of its group in the same claim), and claims
every empty frame in `[from, ge)`: each is marked LOADING and counted in
`n_loading`, so no other worker can pick them and the admission test sees
them as in flight. The worker records the claim on itself and calls
`reader_load_range(from, ge)`.

The deliver callback runs on the loader thread under the cache lock. For a
frame in the worker's claim it does what the old post-decode code did:
`insert_locked()`, which may discard the frame if nothing resident is worth
less, and a wake-up for the main loop; NULL marks the frame FAILED. A frame
outside the claim, or one that became resident meanwhile, is dropped. Then it
decides whether to continue: yes while some later frame of the claim is still
worth having, `score_of(k) < cap_frames`, which with the reserve below means
ahead within the budget or in the reserve; otherwise it releases the rest of
the claim back to EMPTY and returns 0. That early stop is what keeps a
ten-second group from overrunning the budget, and because the reader keeps
`next`, the playhead arriving later resumes from there without a seek.

A cancelled or failed range releases the undelivered claim: to EMPTY on a
cancel, to FAILED on a reader failure so a broken group is not retried
forever. `w->frame` becomes the next frame the worker expects to deliver,
updated in the callback, so `cache_set_focus()`'s staleness test and soft
cancel work per group exactly as they do per frame. `CacheStats.loading`
now counts claimed frames.

### The reserve behind the playhead
`score_of()` orders frames by how much they are worth keeping. Today: frames
ahead within the budget score their distance ahead, everything else is
behind and scores above all of them, farthest first. The reserve inserts one
band. With `reserve` frames protected and `window = cap - reserve` (never
below 2, so the next frame is always ahead):

- ahead by `a < window`: scores `a`
- behind by `b <= reserve`: scores `window + b - 1`
- ahead by `window <= a < cap`: scores `reserve + a`
- behind by `b > reserve`: scores `cap + b`, as today

So the read-ahead fills forwards only up to `window`, never evicts the
reserve to go further, and the reserve is the last thing recycled short of
the frames just shown. `reserve == 0` reproduces today's scores exactly, so
existing behaviour and tests hold until something sets it.

For video the reserve follows the groups: playing forwards from a frame in
group G, it is the frames of G already shown plus the whole of G-1 (the last
group when G is the first, since playback loops); playing backwards, the
frames of G not yet shown plus the whole of G+1. It is recomputed from
`seq->group_start[]`/`group_end[]` whenever the focus or direction changes,
and capped at `cap / 2` so a group larger than the budget still leaves the
other half for the direction of play. For image sequences
`cache_set_reserve(c, n)` sets a fixed count with the same cap; `main.c`
passes one second at the playback rate. This is the mechanism the user asked
for: after a reversal at least a group's worth of frames plays from RAM while
a loader decodes the group beyond it, which takes well under the time that
group takes to play.

### Alternatives considered, one line each
- Write an H.264 decoder to avoid the dependency: months to make bit-exact and fast, and H.265 again after; rejected in discussion.
- Windows Media Foundation: no dependency and hardware decode, but Windows-only, HEVC needs a Store extension, and the Linux build would need a second backend.
- Drop libavformat for an own MP4 demuxer: exact display-order timing and control of reads, but edit lists, fragmented files and moov-at-end are exactly where own demuxers go wrong, and it only removes one of the four libraries; libavformat first, behind an interface an own demuxer can fill later.
- Per-frame picks with a shared decoder: two threads seeking to the same keyframe decode the same frames twice; group claims remove that.
- Deliver a group only when complete: the frame under the playhead would wait for the whole group; incremental delivery shows it the moment it is decoded.
- Cache YUV instead of BGRA to hold nearly three times as many frames: puts conversion on the draw path; deferred.
- Hardware decoding through D3D11 or NVDEC: frames land in GPU memory and must be copied back; software decode is fast enough and keeps every path the same; deferred.
- Read every packet to get exact display-order keyframe positions: reads the whole file once; the decode-order table plus timestamp mapping is exact where it matters.

## Deviations

### The deliver callback carries the failure message
**What came up:** The plan had the callback take `(ud, frame, im)` with NULL
meaning the frame failed, which loses the reason the cache records as its
first error.
**Options:** a separate error slot on the reader; an extra `err` argument.
**Chose:** `ReaderDeliver(ud, frame, im, err)`, `err` set when `im` is NULL.
**Why:** one argument, no extra state, and the EXR backend already has the
message in hand.

### vcpkg's FindFFMPEG enables C++ in a C project
**What came up:** The first configure failed at the generate step: the
module calls `enable_language(CXX)` to learn the C++ runtime libraries
FFmpeg's dependencies need, and CMake refuses a language enabled that late in
a project declared `C` only.
**Options:** declare `C CXX` in `project()`; set the implicit link
libraries by hand so the module skips the call.
**Chose:** `project(ramplayer C CXX)`, with a comment saying why.
**Why:** no C++ source is compiled; the declaration only lets the module do
what it needs.

### Whether a claim continues mirrors the admission test
**What came up:** The plan had a claim continue while a later frame scored
inside the kept set. On an empty cache that stopped every group at the
window and left the free space to be filled one pick at a time, and any rule
that counted the worker's own claims as in flight stopped reverse fills
before their first frame.
**Options:** score only; score or free room; score or free room beyond what
the other workers' claims will take.
**Chose:** the last: a frame is wanted if it scores inside the kept set, or
if there is room for it after the other workers' outstanding claims land.
**Why:** it is the admission test of `pick_locked()` with the worker's own
later claims left out, so a claim stops exactly where a pick would have, and
the group-fill test shows 30 frames delivered for 30 resident with none
discarded.

### Open-group keyframes sit up to three entries early
**What came up:** On the open-GOP fixture the index's keyframe entries are at
decode positions 23, 46 and 70 for display frames 24, 48 and 72: as many
leading B-frames as the encoder reordered, not a fixed one.
**Options:** read every packet to place keyframes in display order; accept
the hint as it is.
**Chose:** accept it, as the plan intended, and test the property rather
than fixed positions: the reader maps every picture by timestamp, the
decode test on that file passes frame for frame, and the retry one group
earlier covers a seek that lands past its range.
**Why:** placing keyframes exactly would mean reading the whole file once.

### A jump forwards within one group decodes on rather than seeking
**What came up:** On the single-keyframe file a request for 50..59 after
0..19 continued decoding from 20 instead of seeking back to frame 0, which
the test had expected to count as a seek.
**Options:** none needed; the behaviour is the cheaper one.
**Chose:** keep it; the test expects it on that file.
**Why:** a seek would have decoded frames 0..49 again.

### Self-review findings (code-review, high)
Seven findings. Six confirmed against the code and fixed, one rejected:
- A frame the decoder never produces (a dropped picture, or a file whose
  frames are not evenly spaced) was neither delivered nor failed, so the
  cache released and re-picked it and the loader redecoded the group without
  end at full CPU. Fixed: gaps between the expected frame and the one that
  arrives are delivered as failures, as the end-of-stream case already was.
- A pick went to whichever worker woke first, so with two loaders a
  single-frame claim often cost a seek and a group redecode, or a decode
  through frames already delivered; a first fix that preferred any positioned
  reader still decoded 76 pictures for 55 frames. Fixed: a worker leaves a
  pick to an idle worker whose reader reaches the range more cheaply, cost
  being the pictures to decode before delivering, with a seek dearer than any
  position in the group. `reader_position()` was added for this, and
  `CacheStats.decoded` so the tests can see it: 55 frames now decode 55
  pictures.
- A callback stopping the range from inside the rejected-packet path was
  taken for the end of the stream, marking the rest failed and mis-setting
  the reader's position. Fixed with a distinct STOPPED code.
- `avcodec_send_packet()` returning EAGAIN dropped the packet. The API rules
  it out after a receive that asked for input, but the packet is now kept
  pending and resent, and a second refusal is reported as a stall.
- Every audio and subtitle packet was read and dropped by hand. Fixed: the
  other streams are marked AVDISCARD_ALL so the demuxer skips them.
- Frames inside a range that the cache had not claimed were still converted
  to BGRA and then thrown away. Fixed: an optional `wanted` query on
  `reader_load_range()`, which the cache answers from its claims; the EXR
  backend skips such frames outright.
- Rejected: building a display-order timestamp table from the index entries
  to place open-group keyframes exactly. The entries carry decode
  timestamps, not presentation ones, so sorting them gives decode order; the
  timestamp mapping of decoded pictures remains the source of truth, as the
  plan says.
